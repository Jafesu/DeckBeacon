What this shows:
- Tools and runtimes (Steam Linux Runtime 1.0–4.0, Proton 9.0/11.0/Experimental) don't have the `BytesToDownload`/`BytesDownloaded`/`BytesStaged` keys. Steamworks Common Redistributables (228980) does have them. So a key's presence doesn't tell you whether an entry is a game or a tool. Game/tool classification needs another source (for example a known list of tool appids, or appinfo, which wasn't examined here).
- After an install finishes, `BytesToDownload`/`BytesDownloaded` keep the last transfer's totals. In every complete manifest except 228980 the two values are equal. They are not live progress.
- `LastPlayed` is not 0 for 7 games, so it is a usable "recently played" signal. Every `LastUpdated` and `LastPlayed` value here is in the 179468xxxx–179487xxxx range.

### What this means for detection
- **Start:** the content_log `state changed` line gains `App Running`, or a process with comm `reaper` and argv `SteamLaunch AppId=<n>` appears. There is **no** "add to running list" line in gameprocess_log, only "adding PID ... as a tracked process".

- Session duration from the logs: 20:15:07 (state → App Running) to 20:17:50 (removed). The two `LastPlayed` writes (launch and exit) can't give a duration once the session is over, because the second write overwrites the first.
- History shows `Remove -50861101 from running list` (2026-11-15 21:18:15): a **negative** AppID, probably a non-Steam shortcut (shortcut app IDs printed as signed 32-bit). The schema has to allow non-Steam shortcut IDs (confirmed in sections 9–11).

### Format
- Binary VDF: type bytes `0x00` map, `0x01` string, `0x02` int32 LE, `0x08` end-of-map. (`0x07` uint64 is handled but wasn't seen.) Root is `shortcuts` → `"0".."7"` → entry.

- Entry keys (name:type): `AllowDesktopConfig:int, AllowOverlay:int, AppName:str, Devkit:int, DevkitGameID:str, DevkitOverrideAppID:int, FlatpakAppID:str, IsHidden:int, LastPlayTime:int, LaunchOptions:str, OpenVR:int, ShortcutPath:str, StartDir:str, appid:int, exe:str, icon:str, sortas:str, tags:dict`.

### What this shows
- **The join works:** the file's `appid` −50861101 is the same ID that appeared as reaper `AppId=4244106195`, as gameprocess_log `AppID 18228297308309553152`, and as `Remove -50861101`. It resolves to `AppName` "Hollow Acre". The file stores the **signed** int32.
- **The appid can't be computed; it has to be read from the file.** For all 8 entries the legacy formula `crc32(exe+AppName) | 0x80000000` does **not** match. Current Steam assigns the ID itself, so the agent must read `appid` from the file.
- `LastPlayTime` = launch time (20:19:37, the same second as the first tracked PID), not exit time. This differs from appmanifest `LastPlayed`, which is written at launch and again at exit.
- AppName isn't unique: "Discord" appears 3 times with different appids. Key by appid, never by name. Some AppNames are just file names (`*.AppImage`, `*_setup_*.exe`), so the UI should show them as-is.
- `FlatpakAppID` is empty even for the Flatpak-launched entries (their `exe` basename is `flatpak`). Chrome is the only entry with `FlatpakAppID` set.
- **Privacy:** `exe`, `StartDir`, `LaunchOptions`, `ShortcutPath` and `icon` contain home paths and possibly arguments. The agent should extract only `appid`, `AppName`, `LastPlayTime`, `IsHidden` (and maybe `tags`), and never send the other fields to HA.

### Proposed agent rule (for the M6 ADR)
Parse shortcuts.vdf on start and when its mtime changes, keeping an allowlist of fields (`appid`, `AppName`, `LastPlayTime`, `IsHidden`). Build a map of u32 appid → name. Normalize every observed ID form (u32, signed int32, 64-bit GameID `>> 32` when `(id & 0xFF000000) == 0x02000000`) to u32 before looking it up. Fallback name: the reaper argv exe basename with its extension removed.
