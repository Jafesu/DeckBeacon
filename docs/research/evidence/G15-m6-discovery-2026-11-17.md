What this shows:
- Tools and runtimes (Steam Linux Runtime 1.0–4.0, Proton 9.0/11.0/Experimental) don't have the `BytesToDownload`/`BytesDownloaded`/`BytesStaged` keys. Steamworks Common Redistributables (228980) does have them. So a key's presence doesn't tell you whether an entry is a game or a tool. Game/tool classification needs another source (for example a known list of tool appids, or appinfo, which wasn't examined here).
- After an install finishes, `BytesToDownload`/`BytesDownloaded` keep the last transfer's totals. In every complete manifest except 228980 the two values are equal. They are not live progress.
- `LastPlayed` is not 0 for 7 games, so it is a usable "recently played" signal. Every `LastUpdated` and `LastPlayed` value here is in the 179468xxxx–179487xxxx range.

### What this means for detection
- **Start:** the content_log `state changed` line gains `App Running`, or a process with comm `reaper` and argv `SteamLaunch AppId=<n>` appears. There is **no** "add to running list" line in gameprocess_log, only "adding PID ... as a tracked process".

- Session duration from the logs: 20:15:07 (state → App Running) to 20:17:50 (removed). The two `LastPlayed` writes (launch and exit) can't give a duration once the session is over, because the second write overwrites the first.
- History shows `Remove -50861101 from running list` (2026-11-15 21:18:15): a **negative** AppID, probably a non-Steam shortcut (shortcut app IDs printed as signed 32-bit). The schema has to allow non-Steam shortcut IDs (confirmed in sections 9–11).

### What this shows

### Proposed agent rule (for the M6 ADR)
Parse shortcuts.vdf on start and when its mtime changes, keeping an allowlist of fields (`appid`, `AppName`, `LastPlayTime`, `IsHidden`). Build a map of u32 appid → name. Normalize every observed ID form (u32, signed int32, 64-bit GameID `>> 32` when `(id & 0xFF000000) == 0x02000000`) to u32 before looking it up. Fallback name: the reaper argv exe basename with its extension removed.

That fits the staged (decompressed) size being larger than the download (here `BytesToStage/BytesToDownload` = 1.036), plus other client writes. `read_bytes` stayed 0 (no disk reads during download). The agent runs as the same user as Steam and can read `/proc/<pid>/io` without privileges.
- wlan0 rx is about 12% above Steam's displayed rate (404 vs 359.5/350.5 Mbps). It includes protocol overhead and all other host traffic, so it is only a cross-check, not a source.

### 13.5 What this means for M6

There is **no on-disk live byte counter** for an active download: the manifest, the `downloading/` tree and content_log all give exact bytes only at events. Live data has to be assembled:

1. **Rate:** latest `Current download rate: X Mbps` from content_log (updated about every 60 s; matches the UI). Smoother option: the delta of `/proc/<steam>/io` `write_bytes` (3 s resolution; ~6% high, measures staged bytes).
2. **Progress:** anchor on the last exact snapshot (`update started : download A/B, … stage C/D` line, or the manifest after a write). Then estimate forward by adding the `write_bytes` delta since that anchor to the staged count (cap at D, and mark the value as estimated). Re-anchor at every event line or manifest write.
3. **State:** from content_log `state changed`/`App update changed` (Running / Suspended / Committing / Fully Installed). StateFlags can't tell running from paused.
4. **ETA:** (B − A_est) / rate, shown only while state = running and rate > 0. Hide or freeze it when paused.
5. Ignore steps where `BytesToDownload == 0` and short sub-steps; prefer the largest `update started` total for the app. The sub-step resets explain the stuck/jumping progress seen in HA.

Not captured: completion of a large download (only the small 4876650 completion was seen), cancel/uninstall mid-download, and a download in Gaming Mode. A disk-full or error case would also be worth seeing. Raw sampler output stays in the session scratchpad and is not committed (it contains the unredacted LAN peer hostname and CDN POP names).
